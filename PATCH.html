Feature Intent

Replace the earlier thread-specific notification implementation with a generic Electron desktop notification abstraction. The first consumer remains opt-in inactive-thread updates, but notification delivery, dedupe, activation routing, and OS-level lifecycle handling now live behind reusable desktop contracts and a main-process service.

Commits

  • 4074465f Redesign the desktop thread notification pipeline.
  • bcb285b8 Merge feature-custom/new-notifications into custom/base.

Implementation Notes

  • desktopThreadNotificationsEnabled is a client-local setting and remains the existing user-facing toggle. Enabling it now sends a generic permission-test notification with short confirmation copy.
  • Notification IPC contracts are generic: requests carry notificationId, dedupeKey, topic, severity, copy, optional route data, and optional ttlMs.
  • Main-process delivery is centralized in DesktopNotificationService, which owns Electron Notification creation, live notification tracking, dedupe TTL, stale notification closing, max-live eviction, failed delivery reporting, and click activation routing.
  • The old ElectronNotifications, threadNotifications.ts, and ThreadNotificationCoordinator implementation were removed. The new renderer coordinator is NotificationCoordinator.
  • Thread-specific derivation now lives in threadActivityNotifications.ts as pure logic. It emits generic notification requests for inactive thread states only.
  • Completion notifications require isLatestTurnSettled, so stale latestTurn.completedAt data cannot notify while the session is still running.
  • Focus suppression no longer consumes an occurrence. If an active focused thread is suppressed and later becomes eligible while inactive or blurred, it can still notify.
  • Initial sidebar snapshots are still seeded per bootstrapped environment so restored state does not emit desktop notifications on launch or when enabling the setting.
  • Occurrence keys are semantic rather than projection timestamp based: pending states key by state and active turn, plan-ready keys by turn and source plan, and terminal states key by turn and terminal timestamp.
  • Browser and unit coverage now spans generic contracts, desktop service delivery, thread activity derivation, coordinator activation routing, bootstrap seeding, focused-active suppression, projection churn dedupe, and state clear/return behavior.

Upstream Merge Context

  • Preserve the desktop bridge boundary; notification APIs should remain desktop-shell specific and reusable rather than thread-specific.
  • If upstream changes sidebar thread summaries, keep thread activity notification priority aligned with visible sidebar state: approvals, user input, plan-ready, failure, then completion.
  • If upstream changes session or turn projection, preserve the settled-turn requirement for completion notifications. A running session must not emit a completed notification because an older turn has completedAt.
  • If upstream changes environment bootstrap or sidebar hydration state, keep notification seeding tied to the first bootstrapped sidebar snapshot for each environment rather than the first render.
  • If upstream changes notification request routing, keep activation payloads generic. Thread routing is one route variant, not the notification service's core model.
  • Signed macOS builds are expected for reliable OS notification delivery. Unsupported or failed delivery must continue to fail gracefully through the generic result path.
