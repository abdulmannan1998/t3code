T3 Code fork workflow

Use this repository as a customized product fork while still being able to pull improvements from the original upstream project.

Current mental model

Treat main as the clean upstream mirror and custom as the long-lived product branch for local customization.

  • upstream/main: original project.
  • origin/main: this fork's clean mirror of upstream.
  • origin/custom: customized product branch.
  • feature/*: individual changes started from custom.

Start a feature

git checkout custom
git pull
git checkout -b feature/my-change

Keep feature branches small enough to review and merge back into custom without mixing unrelated ideas.

Finish a feature

bun fmt
bun lint
bun typecheck
git status
git add .
git commit -m "Add my change"
git checkout custom
git merge feature/my-change
git push

If tests are needed, use bun run test. Do not run bun test in this repository.

Bring in upstream changes

  1. Update the clean mirror branch from the original repository.
  2. Merge that updated mirror into the customized branch.
  3. Resolve conflicts on custom, where the product changes live.
git checkout main
git fetch upstream
git merge upstream/main
git push origin main

git checkout custom
git merge main
git push

Contributing back upstream

If a change should go back to the original project, start that branch from clean main, not from custom. 

git checkout main
git pull origin main
git checkout -b feature/upstream-fix

Safety rules

  • Use merge, not rebase, for the long-lived custom branch.
  • Keep main boring and close to upstream.
  • Make customization decisions on custom, then isolate each feature in a short-lived branch.
  • Run bun fmt, bun lint, and bun typecheck before calling work complete.
